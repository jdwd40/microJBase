# v0.2 Scope

## Product statement

microJBase v0.2 adds deliberately small schema-management capabilities to the v0.1 foundation. A single operator can inspect the database schema, manage tables/columns/indexes/constraints through typed commands, control which tables the data API exposes, and apply predefined row-level-security ownership templates — all behind an opt-in admin boundary that never weakens the v0.1 runtime security model.

v0.2 remains a single-owner, single-VPS product: one Node.js process, one PostgreSQL database, no additional services.

## Required capabilities (planned)

### Read-only schema introspection

- Catalogue of non-system schemas, tables, columns, canonical/underlying type identity, rendered defaults, nullability, ownership, and RLS state.
- Primary-key, unique, foreign-key, and index metadata with ordered columns, referenced targets, actions, uniqueness, and predicate/expression flags.
- Immutable deterministic snapshots that include API exposure state and migration history.
- Unsupported constructs are reported as explicitly classified read-only metadata, never misrepresented.

### Controlled schema mutation

- Typed commands compiled by one audited DDL layer; HTTP handlers never construct SQL.
- Table lifecycle: create, rename, drop (with explicit destructive confirmation).
- Column lifecycle: add, rename, drop; defaults; nullability; a documented safe type-conversion matrix.
- Index and constraint management over verified columns with deterministic or validated names.
- Foreign-key and primary-key management constrained to verified targets and a small action allowlist.
- Transactional execution where PostgreSQL supports it, idempotency/replay keys, advisory serialization, and durable operation history.

### Exposure registry

- Durable registry separating "table exists" from "table is exposed to the data API".
- One-time explicit import/initialisation from `MICROJBASE_TABLES` that preserves existing installations.
- After import, the durable registry is the sole runtime exposure source: the environment variable cannot add tables at runtime and cannot re-expose a table an operator unexposed.
- Runtime reads a verified immutable snapshot; exposure changes apply atomically.

### RLS ownership templates

- Predefined read/insert/update/delete ownership templates bound to `microjbase.user_id`.
- Fail-closed RLS enable/disable rules: disabling requires unexposed state and explicit confirmation.
- No arbitrary policy SQL.

### Admin API (opt-in)

- Disabled unless both a schema-admin database URL and an operator-token SHA-256 digest are configured; configuring exactly one fails startup.
- Separate `/v1/admin/schema` route tree, bounded admin pool, separate rate limiting.
- Read-only endpoints ship before mutating endpoints.
- Single operator bearer token verified by SHA-256 digest with constant-time comparison; the raw token is never stored or logged.

## Security boundaries

- Three PostgreSQL privilege lanes stay distinct: restricted runtime role, explicit migration command role, optional schema-admin owner role.
- The schema-admin role is non-superuser, non-`BYPASSRLS`, owns every table it mutates, and is never the restricted runtime role; it may be the same PostgreSQL role as the migration role but remains a separate request-time connection surface.
- Expose/unexpose applies least-privilege `GRANT`/`REVOKE` for the runtime role and fails closed when required grants are missing; policy commands run only as the table owner, never via superuser escalation or `SET ROLE` to a superuser.
- The runtime role remains non-superuser, non-`BYPASSRLS`, and refuses to start otherwise.
- Internal schemas (`microjbase`, `pg_catalog`, `information_schema`) are permanently ineligible for exposure or destructive mutation.
- Destructive commands require an explicit confirmation value and refuse internal objects.
- An exposed table must be unexposed before destructive mutation.
- No arbitrary SQL endpoint, no arbitrary migration SQL upload, no normal-client SQL endpoint.

## Explicitly out of scope (non-goals)

- A GUI (the queue ends with a stable backend contract ready for a future lightweight GUI).
- Arbitrary policy SQL or custom RLS expressions.
- Expression indexes, raw predicates, and unsupported concurrent index modes (initially).
- Multiple databases or projects per process.
- Accounts, roles, email, OAuth, or another admin auth platform.
- Horizontal scaling, distributed rate limiting, queues, or background workers.
- Supabase/PocketBase compatibility.

## Release gates

- Every queue item V02-00..V02-19 merged with green CI, one active implementation PR at a time, independently reviewed before merge.
- Read-only introspection proves no database mutation.
- Destructive-command and confirmation tests pass, including internal-object refusal.
- Exposure-registry migration from `MICROJBASE_TABLES` is tested on a clean install and on a v0.1 upgrade.
- Admin API tests prove unauthenticated callers and ordinary sessions never reach `/v1/admin/schema`.
- Full unit/integration/E2E suites pass from a clean checkout.
- Documentation and project wiki updated to match the released state.
