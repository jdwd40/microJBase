# v0.2 Architecture

This document describes the target internal shape for v0.2. It is a plan, not a description of implemented code: nothing in this file exists in the repository yet except the v0.1 modules named for context. Implemented v0.1 facts live in [ARCHITECTURE.md](../ARCHITECTURE.md) and [docs/database-spec.md](database-spec.md).

## 1. System shape (target)

v0.2 preserves the v0.1 modular monolith: one TypeScript application, one Node.js process, one PostgreSQL database. No internal network calls, queues, caches, or independently deployed services are added.

```text
HTTP routes (existing /v1/auth, /v1/data)
   |-- Auth service ---- repository contracts ---- PostgreSQL adapters
   |-- Data service ---- repository contracts ---- PostgreSQL adapters
   |-- Core config/errors/logging
   `-- (planned) Admin schema module
          |-- Admin HTTP routes (/v1/admin/schema)
          |-- Schema admin service (typed commands)
          |-- Audited DDL compiler/executor
          |-- Schema introspection readers
          `-- Bounded admin pool (SCHEMA_DATABASE_URL)
```

## 2. Trust and privilege boundaries

Three PostgreSQL privilege lanes remain distinct:

1. **Restricted runtime data role** (`DATABASE_URL`) — used by request handlers; non-superuser, non-`BYPASSRLS`; unchanged from v0.1.
2. **Explicit migration command role** (`MIGRATION_DATABASE_URL`) — used only by the migration command; never by request handlers; unchanged from v0.1.
3. **Optional schema-admin role** (`SCHEMA_DATABASE_URL`) — used only by the planned admin/schema module; disabled by default; requires the module to fail closed on superuser, `BYPASSRLS`, role-management, or unsafe database-wide privilege assumptions.

The admin/schema module is opt-in: it is inert unless both `SCHEMA_DATABASE_URL` and `MICROJBASE_ADMIN_TOKEN_SHA256` are configured.

## 3. Request and operation flows (target)

### Read-only introspection (planned)

1. Admin HTTP route authenticates the operator bearer token (SHA-256 digest comparison, constant time).
2. Schema admin service asks the introspection reader for the requested snapshot.
3. Reader queries PostgreSQL catalogues through the bounded admin pool; no mutation occurs.
4. Service returns an immutable deterministic snapshot including exposure state and migration history.

### Controlled schema mutation (planned)

1. Admin HTTP route authenticates the operator and validates the typed command shape.
2. Schema admin service checks the command against capability and exposure rules (internal-object refusal, exposed-table guards, destructive confirmation values).
3. The audited DDL compiler translates the typed command into parameterised SQL with conservatively validated, quoted identifiers; defaults come from a typed allowlist/template model, never arbitrary SQL.
4. The transactional executor runs the plan inside a transaction where PostgreSQL supports it, under advisory serialization, records the operation (checksum, idempotency key, status, safe actor fingerprint) in durable history, and maps PostgreSQL errors to safe envelopes.
5. The exposure registry is updated atomically where the command affects API exposure.

## 4. The no-arbitrary-SQL rule

- HTTP handlers never construct SQL.
- Application clients (ordinary users) can never reach DDL: there is no normal-client SQL endpoint and no arbitrary migration SQL upload.
- All identifiers pass conservative validation and are quoted by a single audited helper.
- Values remain parameterised where PostgreSQL permits.
- The initial type allowlist is `text`, `integer`, `bigint`, `boolean`, `uuid`, `timestamp`, `timestamptz`, `date`, `numeric`, `jsonb`.

## 5. Exposure registry (target)

- A durable registry separates "table exists" from "table is exposed to the data API".
- Existing installations migrate through a one-time explicit import/initialisation from `MICROJBASE_TABLES`.
- After import, `MICROJBASE_TABLES` cannot re-expose a table an operator unexposed.
- The runtime reads a verified immutable snapshot; exposure changes replace that snapshot atomically.
- Internal schemas (`microjbase`, `pg_catalog`, `information_schema`) are permanently ineligible.

## 6. Compatibility approach

- v0.1 HTTP API behaviour is unchanged: existing auth and data routes keep their contracts.
- v0.1 migrations remain forward-only and immutable; v0.2 adds new forward-only migrations (including the operation-history and exposure-registry tables).
- The runtime role checks at startup keep their v0.1 fail-closed semantics.
- The Fastify `disableRequestLogging` deprecation warning observed during v0.1 is a documentation-time known limitation; v0.2 work does not depend on changing it.

## 7. Module ownership (target)

The planned admin/schema work introduces no new top-level deployable; it extends the existing module layout with clearly owned internals, keeping `contracts/` architect-owned and `pg` imports confined to database/admin adapters. Exact file layout is defined by the implementation PRs in the queue.
