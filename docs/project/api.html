Implemented v0.1 routes

These routes exist on master at the v0.1.0 tag. Base path /v1; JSON is UTF-8. Source: docs/api-spec.md.

Implemented routes
Method and path Purpose Auth
GET /health Liveness and database readiness None
POST /v1/auth/register Register with email and password None
POST /v1/auth/login Login with email and password None
POST /v1/auth/logout Log out the current bearer session Bearer session
GET /v1/auth/me Resolve the current user Bearer session
GET /v1/data/:table List rows with limit/offset Bearer session
GET /v1/data/:table/:id Read one row by UUID id Bearer session
POST /v1/data/:table Insert a JSON object Bearer session
PATCH /v1/data/:table/:id Update one row by UUID id Bearer session
DELETE /v1/data/:table/:id Delete one row by UUID id Bearer session

Only configured aliases such as todos=public.todos are exposed. Table and column identifiers are never accepted blindly, and SQL values are always parameterised.

Planned admin routes (not implemented)

The routes below are planned v0.2 capabilities from docs/v0.2-implementation-plan.md. They do not exist in the repository at v0.2 intake and must not be treated as available.

Planned admin route tree under /v1/admin/schema
Planned surface Planned availability Restrictions
Operator capability/health probe V02-16 Operator bearer token only; startup fails when exactly one of SCHEMA_DATABASE_URL and MICROJBASE_ADMIN_TOKEN_SHA256 is configured, and with neither the module is inert.
Read-only schema snapshots, table details, security state, exposure state, operation history V02-17 Ordinary sessions and unauthenticated callers must never reach these endpoints.
Mutating typed schema commands (table/column/index/constraint/exposure/RLS) V02-18 Requires idempotency keys and explicit destructive confirmations; safe envelopes preserved; no SQL leakage.

Explicit restrictions

  • There is no arbitrary SQL endpoint and no normal-client SQL endpoint in v0.1, and v0.2 does not introduce one.
  • v0.1 has no admin or web dashboard, no email verification, no OAuth/MFA, no file storage, no realtime, and no Supabase API compatibility.
  • The internal microjbase schema is never exposed through the data API.
