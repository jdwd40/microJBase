Implemented v0.1 security boundaries

  • The HTTP layer rejects malformed input and oversized bodies (default maximum body size 1 MiB).
  • The table registry maps a public alias to a configured schema/table; the client never supplies a raw SQL identifier.
  • Database metadata validates body keys as real writable columns before identifiers are quoted.
  • All SQL values use PostgreSQL parameters.
  • Row-level security is the final row-level boundary and is enabled and forced on every exposed table.
  • The runtime database role is non-superuser and non-BYPASSRLS; the server refuses to start otherwise.
  • The microjbase internal schema can never be exposed by the data API; pg_catalog and information_schema are likewise excluded.
  • Logs never contain passwords or raw session tokens; sessions are stored only as SHA-256 digests.
  • Argon2id password hashing with timing-consistent unknown-email handling via a dummy verification.

Fixed MAJOR finding (PR #23)

One MAJOR finding was identified and fixed before the v0.1 release: a real RLS 42501 error on foreign-ownership create/update was mapped to the generic safe 409 CONFLICT envelope, so no SQLSTATE, policy name, RLS wording, or table internals leak through the public error body. The PR #23 GitHub review verified the fix and returned SHIP with 0 blockers, 0 majors, 2 minors.

Known non-blocking limitations (recorded)

Deferred from the security review and recorded in docs/release-checklist.md:

  • No network-level “PostgreSQL unreachable” E2E harness (503 behaviour is unit/integration covered instead).
  • Rate-limiter eviction behaviour at maximum entries.
  • Catch-all 404 uses TABLE_NOT_FOUND naming even for non-table routes.
  • Fastify’s default 415 mapping not customized.
  • Runtime privilege-check placement could be factored into the database module.
  • No policy-expression introspection endpoint (by design).
  • Client-supplied updated_at accepted on rows without an ownership column.
  • Own-UUID ownership comparison is case-sensitive on some paths.
  • Broad 42501 → 409 CONFLICT mapping in the data repository (defence in depth; RLS is the real enforcement boundary).
  • Fastify disableRequestLogging is deprecated for Fastify 6; observed during v0.1, non-blocking for this documentation milestone.

Planned v0.2 admin boundary (not implemented)

Everything in this section is planned capability. At v0.2 intake there is no admin API, no schema mutation endpoint, and no GUI.

  • Admin authorization is a single operator bearer token verified by a configured SHA-256 digest (MICROJBASE_ADMIN_TOKEN_SHA256) with constant-time comparison; the raw token is never stored, logged, or accepted in ordinary user/session auth.
  • The admin/schema module is opt-in: startup fails when exactly one of the schema-admin database URL and the token digest is configured, and with neither the module is inert. It uses a separate /v1/admin/schema route tree, a small bounded admin pool, and separate rate limiting.
  • Destructive schema commands require an explicit confirmation value and refuse internal schemas and objects; an exposed table must be unexposed before destructive mutation.
  • Schema operations are typed commands compiled by one audited DDL layer; HTTP handlers never construct SQL; no arbitrary SQL endpoint or migration SQL upload is introduced.
  • A third privilege lane (SCHEMA_DATABASE_URL) stays separate from the runtime and migration roles and connects as a non-superuser, non-BYPASSRLS owner of every table it mutates; it may share the migration role but never the runtime role, applies least-privilege runtime GRANT/REVOKE on expose/unexpose with fail-closed missing grants, and runs policy commands only as the owner — never via superuser escalation or SET ROLE to a superuser.
