# v0.1 Scope

## Product statement

microJBase v0.1 is the smallest practical self-hosted backend that lets a first-party application register users, create revocable sessions, and perform user-authorised CRUD against selected PostgreSQL tables.

It targets a single owner, one VPS, modest traffic, and one PostgreSQL database. It is not a multi-tenant backend hosting platform.

## Required capabilities

### Authentication

- Register with email and password
- Login with email and password
- Logout the current bearer session
- Resolve the current user
- Argon2id password hashing
- Opaque random sessions stored only as SHA-256 hashes
- Configurable session expiry
- Basic bounded rate limiting for register/login

### Data

- Explicit alias-to-table allowlist
- List rows using limit/offset
- Read one row by UUID `id`
- Insert a JSON object
- Patch one row by UUID `id`
- Delete one row by UUID `id`
- PostgreSQL RLS enforced with a transaction-local user identity
- Metadata validation of writable column names

### Platform

- Environment configuration validated at startup
- Ordered SQL migrations
- Restricted runtime database role checks
- JSON logs with secret redaction
- Stable JSON response/error envelope
- Liveness/readiness health endpoint
- Graceful shutdown
- Unit, integration, end-to-end, security, and footprint tests

## Explicitly out of scope

- Email verification or any outbound email
- Forgotten-password flow
- Password change endpoint
- OAuth, magic links, MFA, anonymous users, or roles/teams
- Admin or web dashboard
- Storage or signed files
- Realtime/WebSocket/SSE
- Functions/RPC, webhooks, queues, cron, or background workers
- Arbitrary SQL, joins, aggregates, general filtering, or GraphQL
- API keys, service-role tokens, or per-project provisioning
- Multiple databases/projects managed by one process
- Horizontal scaling or distributed rate limiting
- Supabase/PocketBase compatibility
- SDK generation

## Proof-of-life acceptance flow

On a clean PostgreSQL database:

1. Migrations complete.
2. microJBase starts with a restricted runtime role and one exposed `todos` table.
3. Alice registers and receives a session token.
4. Alice creates and reads a todo.
5. Bob registers and cannot read, update, or delete Alice's todo.
6. Alice logs out and her token can no longer access `/v1/auth/me` or data routes.
7. Restarting the API preserves users, sessions, and data.
8. The complete flow passes via HTTP in an automated end-to-end test.

## Release gates

- All documented endpoints and error cases behave as specified.
- No critical or high adversarial-review findings remain open.
- Runtime-role and RLS fail-closed tests pass.
- Unit, integration, and e2e suites pass from a clean checkout.
- Migration up/down policy is documented (v0.1 migrations are forward-only).
- Idle RSS, startup, and simple load measurements are recorded.
- Deployment, backup, restore, and upgrade instructions are verified on Linux.

Any feature outside this file requires a scope decision before implementation.
